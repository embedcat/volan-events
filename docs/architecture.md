# Архитектура

Пункты с пометкой *(предложение)* ещё не обсуждались — см. [open-questions.md](open-questions.md).

## Обзор

```
 браузер организатора (PWA)          сервер (VPS)                 браузер гостя
┌──────────────────────────┐       ┌───────────────────────┐     ┌──────────────┐
│ SvelteKit SPA            │ HTTP  │ Fastify               │ SSE │ SvelteKit SPA│
│ domain (правила турнира) │──────►│ domain (те же правила)│────►│ только чтение│
│ IndexedDB: события,      │◄──────│ SQLite (Drizzle)      │     └──────────────┘
│ справочник, очередь      │  SSE  └───────────────────────┘
│ команд на отправку       │
└──────────────────────────┘
```

- **Пакет `domain`** — правила турнира на чистом TypeScript: генерация кругового расписания,
  проверка счёта, таблица мест, подсказка матча на корт, применение команд к состоянию.
  Один и тот же код работает в браузере и на сервере.
- **При наличии интернета** главный — сервер. Без интернета устройство работает само
  и копит команды.
- **Без интернета событие ведут с одного устройства** (договорённость, а не техническое
  ограничение). Если всё же правили с двух, при синхронизации возникают конфликты.

## Изменения как команды

Любое изменение — команда: «добавить участника», «вызвать матч на корт», «ввести счёт»,
«исправить счёт», «выключить корт» и т. д.

Команда содержит: ID (генерирует клиент), событие, тип, данные, устройство, пользователя,
время на устройстве.

- **Онлайн.** Клиент применяет команду у себя сразу (интерфейс не ждёт сети) и отправляет
  на сервер. Сервер проверяет её правилами из `domain`, применяет, присваивает порядковый
  номер в событии и рассылает всем подписанным через SSE.
- **Оффлайн.** Клиент применяет команду у себя и кладёт её в очередь на отправку
  (IndexedDB). Интерфейс показывает «нет связи, N изменений ждут отправки».
- **Синхронизация.** При появлении связи очередь отправляется по порядку. Сервер заново
  применяет каждую команду к своему актуальному состоянию:
  - команда корректна — принимается;
  - совпадает с уже применённой (тот же счёт того же матча) — принимается без изменений;
  - противоречит (матч уже закрыт с другим счётом, корт занят, матч уже на корте) —
    записывается как конфликт. Клиент получает актуальное состояние сервера,
    а организатор видит список конфликтов и выбирает вариант.

Требования к `domain`, чтобы это работало *(предложение)*:

- команды детерминированы: случайность (жеребьёвка) передаётся в команде как зерно
  генератора, ID новых сущностей генерирует клиент (UUIDv7);
- применение команды — чистая функция `(состояние, команда) → новое состояние | ошибка`.

## Оффлайн

- Приложение кешируется service worker'ом (vite-plugin-pwa) и открывается без сети.
- Каждое открытое событие и справочник игроков сохраняются в IndexedDB (Dexie).
- Без интернета можно создать событие и новых игроков — они уйдут на сервер позже.
- Вход требует сети хотя бы один раз. Дальше сессия живёт долго и работает без сети.
  Если к моменту синхронизации сессия истекла — повторный вход, очередь команд сохраняется.
- Гости видят последнее состояние, дошедшее до сервера, с отметкой «обновлено в ЧЧ:ММ».

### iPhone и iPad

Safari может удалить данные сайта, который не открывали около недели и который не установлен
на экран «Домой». Поэтому:

- инструкция для организатора: установить приложение на экран «Домой»
  и открыть событие перед выездом, пока есть интернет;
- приложение запрашивает постоянное хранилище (`navigator.storage.persist()`);
- выгрузка события в JSON — страховка от потери данных.

## Время

Время вызова на корт и ввода результата берётся с устройства, отправившего команду.
Сервер дополнительно записывает время получения.

## Обновления в реальном времени

- Команды — обычные HTTP-запросы (POST).
- Изменения приходят по SSE: поток на событие. При переподключении клиент передаёт номер
  последнего полученного изменения и получает пропущенное.
- В nginx для SSE отключается буферизация.
- Гостевой поток не должен содержать закрытых полей игрока (год рождения, контакт).

## Хранение на сервере

SQLite через Drizzle (драйвер better-sqlite3).

- Пользователи, сессии, справочник игроков, список событий — обычные таблицы.
- Внутреннее состояние события — журнал команд + снимок текущего состояния
  *(предложение; обсудить на этапе модели данных)*.

## Аутентификация

Логин и пароль, хеш паролей argon2id, серверная сессия в SQLite, cookie
httpOnly + Secure *(предложение)*. Суперюзер создаётся консольной командой.

## Стек

| Часть | Выбор |
|---|---|
| Язык | TypeScript везде |
| Среда сервера | Node.js 24 LTS |
| HTTP-сервер | Fastify |
| База | SQLite, Drizzle ORM, better-sqlite3 |
| Схемы и проверка данных | Zod (общие для клиента и сервера) |
| Интерфейс | Svelte, SvelteKit в режиме SPA |
| Работа без сети | vite-plugin-pwa (service worker), Dexie (IndexedDB) |
| Обновления | SSE + HTTP |
| Монорепозиторий | pnpm workspaces |
| Тесты | Vitest; позже Playwright для сценариев в браузере |
| CI | GitHub Actions |
| Оформление | свой минимальный CSS, светлая и тёмная тема по системе, без UI-библиотек |

Код и идентификаторы — на английском, комментарии и документация — на русском,
интерфейс — только на русском.

## Структура репозитория

```
packages/
  domain/   правила турнира, команды, схемы Zod; без зависимостей от браузера и Node
  server/   Fastify, Drizzle, SQLite, SSE, консольные команды
  web/      SvelteKit SPA, PWA, Dexie
docs/
```

## Размещение

- VPS в РФ, тот же, что у rockevents. Docker + nginx.
- Адрес: volan.rockevents.ru.
- Один контейнер: Fastify отдаёт API и собранный SPA *(предложение)*.
  nginx снаружи проксирует запросы и держит HTTPS.
- Файл SQLite — в томе Docker, регулярная резервная копия *(предложение: как и куда — обсудить)*.
- Репозиторий — GitHub.
